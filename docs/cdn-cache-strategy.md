# CDN cache strategy

Issue #333 found that the only cache directive anywhere in this repository was the
`max-age=60` on the synthetic 404, and that the policy separating long-lived hashed
assets from short-lived HTML — if one existed — lived only in the CodePipeline and
CloudFront configuration of the infrastructure repository, invisible to anyone reading
this one. This document is the in-repo half of that policy: the cache classes the static
export produces, the `cache-control` each class needs, and where that contract is (and
is not yet) proved.

## Who sets what

[ADR 0001](adr/0001-static-export-s3-cloudfront.md) ships `out/` to S3 behind CloudFront;
the deploy job only _triggers_ the pipeline
([deployment runbook](deployment-runbook.md)). Three places can put a `cache-control`
header on a response, and only one of them is in this repository:

- **S3 object metadata**, written by the pipeline's upload step
  (`website-infrastructure`) — the origin `cache-control` per object, keyed by path or
  type.
- **CloudFront cache policy and response-headers policy** (`website-infrastructure`) —
  how long the edge keeps an object, and the headers added on the way out.
- **`scripts/cloudfront_routing.js`**, the viewer-request function (this repository) —
  the synthetic 404 only: `public, max-age=60`.

So this page is a **contract the infrastructure must satisfy**, derived from what
`make build-out` actually emits, not a description of a setting this repository can
change. The classes below are the request; the [verification](#where-the-contract-is-proved)
section is honest about how much of it is currently observed.

## The three cache classes

Every path the export produces falls into exactly one of these. The edge allow-list in
`scripts/cloudfront_routing.js` (see [edge-routing.md](edge-routing.md)) already
partitions the same set, so a path that reaches the origin is always one of them.

### 1. Content-addressed — `/_next/static/**`

Everything Next writes under `_next/static/` carries a content hash in its name or sits
under a per-build id directory: chunks (`chunks/<id>.<hash>.js`), stylesheets
(`css/<hash>.css`), the `next/font` files (`media/<hash>-s.p.woff2`), the SVGs imported
from `src/`, and every raster `next-export-optimize-images` writes
(`chunks/images/**/<name>.<hash>_<width>.webp`, see `export-images.config.js`). A new
build never overwrites one of these paths with different bytes; it emits new paths.

Required header:

```text
cache-control: public, max-age=31536000, immutable
```

`immutable` is what stops browsers revalidating on reload; the year is the RFC 9111
ceiling clients honour. Nothing needs invalidating in this class, ever, which is why
hashed paths can make up the bulk of the edge allow-list at no operational cost.

### 2. Un-hashed — documents, metadata, and `public/` copies

The route documents (`index.html`, `en.html`, `swagger.html`, `en/docs/api.html`,
`404.html`, `offline.html` — the set in `config/routes.json` plus the two error
documents), `swagger-schema.json`, `robots.txt`, `sitemap.xml`,
`.well-known/security.txt`, `sw.js`, and every file copied verbatim from `public/`
(`favicon.svg`, `layout/**`, `images/**`). These paths are stable across builds and their
bytes change on every deploy, so a long browser TTL here is a stale site.

Required header:

```text
cache-control: public, max-age=0, must-revalidate
```

The browser may keep a copy but must revalidate it; S3 serves an `ETag`, so a
revalidation of an unchanged document costs a `304`, not a transfer. CloudFront may hold
these objects longer through `s-maxage` or its cache policy **only if** the deploy makes
the new build visible inside the readiness window the post-deploy smoke test already
assumes — about ten minutes (`docs/deployment-runbook.md`, "Post-deploy smoke test").
The pipeline meets that either by invalidating this class after the upload or by keeping
the edge TTL under the window; which one is the infrastructure repository's decision.
The readiness probes only sample this class — they fetch `/` and `/swagger` — so a stale
un-probed object (`sw.js`, `swagger-schema.json`, another route document) passes them
today; covering the rest is part of the probe described under
[verification](#where-the-contract-is-proved).

Two entries in this class are stricter than the rest:

- `sw.js` — a service-worker script fetched from a long-lived cache can pin an old
  `offline.html` for as long as the browser's update check tolerates. Serve it with
  `max-age=0`; the worker itself is deliberately not a caching layer
  ([offline-shell.md](offline-shell.md)).
- `swagger-schema.json` — regenerated from the pinned contract on every build; a stale
  copy shows the previous API version on `/swagger` under the current one's document
  version.

### 3. The synthetic 404

Generated by the viewer-request function before the cache, so CloudFront never stores
it. `scripts/cloudfront_routing.js` sets `cache-control: public, max-age=60` itself so a
browser may hold a negative response for at most a minute — long enough to absorb a
retry storm, short enough that a route added by the next deploy is reachable
immediately. This is the one directive the repository owns outright;
`src/test/edge/cloudfront-routing.test.ts` pins the exact value on every PR.

## Continuous deployment and staging

`lighthouserc.*.js` and `src/test/load/config.json.dist` send an
`aws-cf-cd-<NEXT_PUBLIC_CONTINUOUS_DEPLOYMENT_HEADER_NAME>` header. That is CloudFront's
continuous-deployment mechanism: a request carrying the header is routed to the staging
distribution, which is how a new build can be measured before it is promoted. The header
name and value are infrastructure values (`.env` ships placeholders); the cache classes
above apply to both distributions identically.

## Where the contract is proved

- _Every exported path is in exactly one class_ — `scripts/ci/verify-edge-allowlist.mjs`
  runs the edge handler over `out/` on every PR.
- _The synthetic 404 carries `max-age=60`_ — `src/test/edge/cloudfront-routing.test.ts`,
  in the 100 % `edge` layer.
- _The security headers reach the live edge_ — the `deploy.yml` post-deploy header probe,
  once `PRODUCTION_SITE_URL` is set.
- _A deploy becomes visible within the window_ — the readiness probes in `deploy.yml`,
  which retry until the new build is served on `/` and `/swagger`; the other class-2
  paths are not sampled.
- _Classes 1 and 2 carry the headers above_ — **not yet observed**; see below.

The last item is the honest gap. Nothing in this repository can read the S3 metadata
or the CloudFront cache policy, so the only place the class headers can be checked is
the live response. The intended assertion is a probe in
`scripts/ci/smoke-response-shape.sh` that fetches `/` (class 2) and one path under
`/_next/static/` read from the served HTML (class 1) and grades their `cache-control`
against the two values above — `::warning::` first, promoted to blocking after one green
deploy has reported no warnings, the same rule the header check on the 404 follows. It
lands once `PRODUCTION_SITE_URL` is set and the first live reading exists to calibrate
against; landing it blind risks reddening every deploy for a header this repository does
not own.

## Changing a class

- A new page is class 2 by construction; register it per
  [extending-the-website.md](extending-the-website.md) and nothing here changes.
- A new `public/` file is class 2. If it is large and immutable in practice (a font, a
  video), import it from `src/` instead so it is hashed into class 1 — do not add a
  per-file TTL exception to the infrastructure for it.
- Never move a class-2 path to class 1 by giving it a long TTL: an un-hashed path with
  `immutable` is a stale site until every visitor's cache expires, and there is no
  in-repo way to shorten that afterwards.
